## Audit Summary

BrandOS has a strong product vision: a local AI-powered personal brand operating system that turns real projects into LinkedIn content, review workflows, publication tracking, assets, and learning loops. The current codebase has outgrown its original MVP boundary. The main issue is not lack of features; it is that many features now share an unstable center.

- `app/core/brandos_service.py` is a 156 KB service object that owns generation, CMO recommendations, briefings, publication state, scheduling, metrics, strategic memory, registry cleanup, and publishing workflows.
- `data/registry/publication-log.json` is used as multiple shapes at once: mostly a list of weeks with nested `items`, but also containing root-level loose test items. Some code also expects a dict with an `items` key.
- Web routes instantiate `BrandOSService()` directly at import time, which makes dependency injection, test isolation, and LLM avoidance harder.
- The current verification baseline fails: `python -m pytest -q` reports `1 failed, 27 passed`, with `tests/test_brandos_service.py::test_get_dashboard_metrics` expecting 3 items while the current dashboard logic counts 2 main publication items.

## Direction Suggestions

- Build around one daily operator screen: "What should I publish, improve, or learn today?" Evidence: the repo already has calendar, CMO recommendations, briefings, publication assistant, metrics, and strategic memory, but they are separate pages and service methods.
- Treat `Publication` as the product central object, not "generated week". Evidence: assets, metrics, scheduling, publishing, and learning all attach to individual posts, while weeks are generation batches.
- Keep LinkedIn publication manual, but make the manual step excellent: preflight checklist, copy-ready text, first comment, asset bundle, publish link capture, and metric reminders. This matches `docs/01-product-vision.md` principles of human review and no auto-publishing.
- Add a "campaign" concept only after the registry is stable: a 30-day campaign around a project can connect weekly planning, content mix, metrics, and portfolio outcomes without turning every feature into another isolated page.

## Findings Considered And Rejected

- Full database migration to SQLite immediately: useful later, but too much blast radius before the registry schema is normalized and covered by tests.
- LinkedIn API or scraping integration: explicitly out of MVP scope in docs and unnecessary for the current goal of building a manual, reliable content workflow.
- Rebuilding the UI framework: the problem is domain flow and backend state, not HTML/CSS technology.
